# 代码审查规范

> 参考来源：Google eng-practices、Microsoft 工程实践、SmartBear、Atlassian、Nerdify 2025
>
> 角色定位：本文件只规定**审查维度 + 输出格式 + 流程**。接口契约核查的完整 17 项清单、Testcontainers 集成测试代码见 [integration-test.md](integration-test.md)。


## 一、审查清单（11 个维度，速查用）

### 1. 设计与架构
- [ ] 整体设计是否合理，代码交互是否符合系统架构
- [ ] 变更是否应放在当前代码库，还是独立模块/库
- [ ] 是否过度设计（解决今天的问题，不猜测未来需求）
- [ ] 分层是否正确：Controller 不写业务逻辑，Service 不写 SQL，DAO 不写业务判断
- [ ] 是否引入了循环依赖
- [ ] 是否正确使用设计模式（不过度，也不缺失）
- [ ] 接口契约是否被破坏（不改变已有 API 的行为约定）

### 2. 功能与正确性
- [ ] 代码是否实现了需求/工票描述的功能
- [ ] 边界情况是否处理（null、空串、边界值、溢出）
- [ ] 并发场景是否考虑（竞态条件、死锁、线程安全）
- [ ] off-by-one 错误、数学精度是否验证
- [ ] 用户可见的变更是否实际验证过（UI 变更要试用）

### 3. 可读性与可维护性
- [ ] 命名是否清晰表达意图（不用缩写，如 `calcRev` → `calculateGrossRevenue`）
- [ ] Java：PascalCase 类名 / camelCase 方法变量 / UPPER_SNAKE_CASE 常量
- [ ] JS/TS：camelCase 变量函数 / PascalCase Vue 组件
- [ ] 数据库：snake_case 表名字段
- [ ] 函数是否短小且职责单一（理想 < 20 行）
- [ ] 代码逻辑是否清晰，新人能否快速理解
- [ ] 是否存在死代码、注释掉的代码块（应删除）
- [ ] 是否有 god class、过度嵌套、魔法数字/字符串
- [ ] 注释只解释 WHY，不解释 WHAT；清除过期 TODO

### 4. 安全
- [ ] 所有用户输入是否校验和清洗（SQL 注入、XSS、CSRF 防护）
- [ ] 敏感信息是否硬编码（API Key、密码、Token → 用 vault/env 配置）
- [ ] 每个接口是否都有鉴权校验（认证 + 授权）
- [ ] 错误信息是否泄露内部细节（不暴露堆栈、数据库结构）
- [ ] 第三方依赖是否有已知漏洞（CVE 检查）
- [ ] 密码是否用 BCrypt 等安全算法存储
- [ ] CORS 配置是否合理

### 5. 性能
- [ ] 算法复杂度是否合理（避免 O(n^2) 能用 O(n) 的场景）
- [ ] 是否有 N+1 查询问题（JPA 用 `@EntityGraph` / `JOIN FETCH`）
- [ ] 大数据量是否分页或流式处理，不全量加载
- [ ] 高频访问数据是否考虑缓存（`@Cacheable`）
- [ ] 资源是否正确关闭（连接、流、文件句柄）
- [ ] 网络请求是否合并（减少不必要的多次调用）
- [ ] `@Transactional` 是否用在正确的粒度（方法级，不在循环内）

### 6. 异常处理与日志
- [ ] 捕获具体异常，不捕获 `Exception` 或 `Throwable`
- [ ] 不吞异常，不用 `printStackTrace`
- [ ] 日志是否包含上下文（用户ID、请求ID、文件名、堆栈）
- [ ] 用户侧错误信息是否友好（不暴露技术细节）
- [ ] 异常路径下资源是否正确释放（try-with-resources / finally）
- [ ] 统一使用 `BizException` + `Result<T>` 包装返回

### 7. 测试
- [ ] 变更是否包含对应的测试代码（同一 CL/PR）
- [ ] 测试是否真正验证核心逻辑（不是只测了 trivial 场景）
- [ ] 是否覆盖了正常路径 + 异常/边界路径
- [ ] 是否用**等价类划分**减少了冗余用例，同时保证覆盖所有等价类
- [ ] 是否用**边界值分析**覆盖了 min / min-1 / max / max+1
- [ ] 多条件业务逻辑是否用**判定表**覆盖了关键条件组合
- [ ] 有状态业务是否测试了**合法/非法状态转换**
- [ ] 是否覆盖错误推测场景：null、空串、重复提交、并发、超时
- [ ] 测试命名是否表达意图（`test_fail_when_duplicate_email` 而非 `test_user`）
- [ ] 测试是否独立、可重复、不依赖执行顺序
- [ ] 测试代码本身是否简洁（测试也需要维护）
- [ ] **接口变更**必须含 8 类集成测试用例（见 [integration-test.md §5](integration-test.md#5-用例设计矩阵每个端点至少覆盖-8-类)）

### 8. 前端专项（Vue3 + Ant Design Vue）
- [ ] 是否使用 `<script setup>`，没有 Options API
- [ ] 是否有 `any` 类型（严格禁止）
- [ ] Props / Emits 是否定义了类型和校验
- [ ] `v-for` 是否有唯一 `:key`
- [ ] `v-html` 是否处理了 XSS 风险（禁止用于用户输入）
- [ ] 异步操作是否有 loading 状态和错误处理
- [ ] 路由守卫是否正确配置（需登录页面）
- [ ] 组件是否可复用，职责是否单一
- [ ] 计算属性 vs 方法 vs watch 是否选择正确
- [ ] 大列表是否考虑虚拟滚动
- [ ] API 调用是否集中管理（Axios 拦截器统一处理 token/错误）
- [ ] localStorage/sessionStorage 是否存放了敏感信息（XSS 风险）

### 8.1 前后端联调审查（组件-接口绑定 + 数据流闭环）
- [ ] 每个按钮/下拉框/搜索框 `@click` 事件是否追溯到正确的 API 函数，参数名/类型与后端 DTO 一致
- [ ] 编辑按钮是否先调用详情 API 回显数据，表单字段名与后端 VO 一致
- [ ] 删除按钮是否有二次确认弹窗，传 `row.id` 而非硬编码
- [ ] 新增/编辑/删除成功后是否调用 `fetchList()` 刷新列表
- [ ] 下拉框 options 是否从 API 获取，`@change` 是否触发对应查询
- [ ] 分页组件切换后是否调用列表 API，参数名与后端一致
- [ ] 接口失败是否有 `catch` + toast 提示（禁止无错误处理）
- [ ] 表单校验 `rules` 与后端 DTO 注解对齐（`required` ↔ `@NotBlank`）
- [ ] 按钮/菜单权限显示隐藏与后端 `@SaCheckPermission` 一致
- [ ] 空列表时是否有占位提示，loading 状态是否正确显示

### 8.2 UI 布局审查（美观 + 无遮挡 + 无重叠）
- [ ] 弹窗/抽屉 `z-index` 高于 header/sidebar，不遮挡操作按钮
- [ ] 同级元素用 flex/grid 布局，不靠 absolute 定位堆叠
- [ ] 长文本容器有 `truncate` 或 `overflow-hidden`，表格列设置 `ellipsis`
- [ ] 组件间距用 Tailwind `gap-`/`p-`/`m-` 系统类，无内联魔法间距
- [ ] 外层容器用 `flex-1`/`w-full`/`min-w-0`，不写死像素宽度
- [ ] 表单用 `a-form-item` 统一对齐，按钮组用 `a-space`
- [ ] `<a-table>` 每列 `width` 明确，总宽度不超容器
- [ ] 弹窗 `width` 适配内容，长表单用 `drawer` 替代 `modal`
- [ ] 弹窗内容超长时有 `max-h-[60vh] overflow-y-auto`
- [ ] 无横向滚动条（页面级别和弹窗级别都需检查）

### 9. 后端专项（Spring Boot）
- [ ] API 返回统一用 `Result<T>` 包装
- [ ] HTTP 状态码是否正确（200/201/204/400/404/500）
- [ ] 接口是否有 Swagger/OpenAPI 文档
- [ ] DTO/VO/Entity 是否分层使用（不直接暴露实体）
- [ ] 入参是否用 `@Valid` + Bean Validation 校验
- [ ] 数据库索引是否加在高频查询字段上
- [ ] 是否有批量插入/更新（避免循环内单条操作）

### 10. 风格与一致性
- [ ] 代码风格是否符合团队规范（ESLint / Checkstyle 通过）
- [ ] 风格变更和功能变更是否分开提交（不混在同一个 PR）
- [ ] 与现有代码库保持一致（优于个人偏好）
- [ ] 格式化是否由工具自动处理（不人工讨论空格/缩进）

### 11. 测试与构建
- [ ] 构建是否通过（`pnpm build` / `mvn clean install`）
- [ ] Lint 是否通过（`pnpm lint`）
- [ ] 测试是否通过（`mvn test`，含 `*ApiTest`）
- [ ] 提交信息格式：`feat(scope): 描述` / `fix(scope): 描述`


## 二、审查输出格式

```markdown
## 审查结果

### 问题
1. **[严重]** `UserService.java:42` — Service 层直接写了 SQL，违反分层原则
2. **[建议]** `Login.vue:15` — 异步请求缺少 loading 状态和错误处理
3. **[Nit]** `UserMapper.xml:8` — SELECT * 应明确字段，避免多余列传输

### 优点
- 异常处理统一，BizException + @ControllerAdvice 使用规范
- 分页接口设计合理，PageHelper 使用正确
- 单元测试覆盖了主要边界情况
```

**严重程度说明**：

| 标签 | 含义 | 处理 |
|------|------|------|
| **[严重]** | 安全漏洞、逻辑错误、数据损坏风险、架构违规 | 必须修复才能合并 |
| **[建议]** | 性能隐患、可维护性差、缺测试、缺错误处理 | 强烈建议修复 |
| **[Nit]** | 命名偏好、风格细节 | 不阻塞合并，可后续优化 |


## 三、审查原则（来自 Google & Microsoft）

1. **代码健康度是标准**：代码不需要完美，但必须比修改前更好
2. **优先审批**：一旦变更确实提升了系统整体健康度，即使不完美也应批准
3. **解释 WHY**：每条反馈说明原因，不是只说"改掉"
4. **肯定好代码**：看到好的实践要明确表扬，不要只挑毛病
5. **先看测试**：测试能揭示作者的意图和预期行为，先审测试再审实现
6. **关注上下文**：看完整文件，不只看 diff；评估对系统整体的影响
7. **及时反馈**：审查延迟会阻塞整个团队，安排固定的审查时间
8. **自动化优先**：格式、风格、Lint 等交给工具，人专注于逻辑和设计


## 四、审查流程建议

| 环节 | 要求 |
|------|------|
| 提交前 | 作者自审代码，运行测试，提供清晰的变更说明 |
| 审查量 | 单次审查 < 400 行（Cisco 研究：超过 200 行缺陷发现率急剧下降） |
| 审查时长 | 单次不超过 60 分钟，超过后休息再继续 |
| 审查人数 | 2 名活跃审查者为宜 |
| 反馈优先级 | 正确性 → 设计 → 安全 → 性能 → 可读性 → 风格 |
| 修复确认 | 发现的缺陷必须记录并验证已修复 |


## 五、前后端接口契约一致性审查（6 项核心 + 详细）

> 完整 17 项核对清单、不匹配清单模板、鉴权矩阵、禁止事项等见 [integration-test.md §5 API Contract Review](integration-test.md)。
>
> 本节是 PR 合并前的**强制门禁**，前后端联调前必查。

### 5.1 必查 6 项（每项都通过才能合并）

- [ ] **数量一致**：后端 `@*Mapping` 数量 == 前端 `api/*.ts` 中 export 函数数量（±0，禁止多调或死接口）
- [ ] **路径 + 方法一致**：HTTP 方法、URL、前后缀斜杠完全匹配（错配 404/405）
- [ ] **请求参数一致**：Path / Query / Body 字段名、类型、必填、枚举值一一对应（**禁止** 前端 `page_num` 调后端 `pageNum`）
- [ ] **响应结构一致**：`Result<T>` 的 `code` / `msg` / `data` / `traceId` 三端对齐（成功 `code=200`），空值/大数字序列化策略一致
- [ ] **鉴权一致**：每个接口的 `@SaCheckRole` / `@SaCheckPermission` 与前端 `meta.roles` 字符串完全一致（区分大小写）
- [ ] **越权必须 403**：越权访问（USER 调 ADMIN 接口）必须返回 `code=403` 而非 404（避免信息泄露）

### 5.2 快速核对（接口清单收集）

```bash
# 1. 后端接口清单
grep -rE "@(Get|Post|Put|Delete|Patch)Mapping" backend/src/main/java \
  | sed -E 's/.*@(Get|Post|Put|Delete|Patch)Mapping\(["\(]?([^")]*).*/\1 \2/' \
  | sort -u > /tmp/backend-apis.txt

# 2. 前端 axios/ofetch 调用清单
grep -rE "request\.(get|post|put|delete)|axios\.(get|post|put|delete)" frontend/src \
  | sed -E 's/.*request\.(get|post|put|delete)\(['"'"'"]([^'"'"'"]+).*/\1 \2/' \
  | sort -u > /tmp/frontend-apis.txt

# 3. 取差集
diff /tmp/backend-apis.txt /tmp/frontend-apis.txt
```

详细自动化收集 + 17 项核对清单 + 鉴权矩阵 + 一致性对照表模板 + 禁止事项 → [integration-test.md §5](integration-test.md)。


## 六、禁止事项

| 类别 | 禁止 |
|------|------|
| **审查态度** | ❌ 人身攻击；❌ 完美主义阻塞 PR；❌ 不解释原因就拒绝 |
| **审查范围** | ❌ 单次审查 > 400 行；❌ 不看 PR 描述就开审；❌ 跳过 CI 检查 |
| **输出** | ❌ 只说"不行"不说"为什么"；❌ 混用严重/建议等级；❌ 复述代码而非指出问题 |
| **测试** | ❌ 接口 PR 无 `*ApiTest` 就合并；❌ 测试覆盖率下降不阻断；❌ Mock Mapper 跳过真实 DB |
| **安全** | ❌ 密码明文；❌ API Key 提交；❌ 越权返 404；❌ 错误信息暴露堆栈 |
| **流程** | ❌ 24h 不响应；❌ 不在 PR 描述中说破坏性变更；❌ 数据库迁移与代码不同步 |

## 开发规则整合

### 架构设计
- 优先采用当前主流且经过生产验证的企业级方案
- 以中型公司实际落地标准设计
- 满足业务需求即可，不允许过度设计

### 编码原则
- 使用最少代码完成需求
- 优先可读性，其次是代码量
- 避免重复代码（DRY）

### 代码要求
- 所有代码必须包含中文注释
- 必须进行必要的判空处理
- 必须进行必要的异常处理

### 性能原则
- 先保证正确性
- 再保证可维护性
- 最后再考虑性能优化
