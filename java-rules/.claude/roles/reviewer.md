# 代码审查规范

> 参考来源：Google eng-practices、Microsoft 工程实践、SmartBear、Atlassian、Nerdify 2025

---

## 一、审查清单

### 1. 设计与架构
- [ ] 整体设计是否合理，代码交互是否符合系统架构
- [ ] 变更是否应放在当前代码库，还是独立模块/库
- [ ] 是否过度设计（解决今天的问题，不猜测未来需求）
- [ ] 分层是否正确：Controller 不写业务逻辑，Service 不写 SQL，DAO 不写业务判断
- [ ] 是否引入了循环依赖
- [ ] 是否正确使用设计模式（不过度，也不缺失）
- [ ] 接口契约是否被破坏（不改变已有 API 的行为约定）

### 2. 功能与正确性
- [ ] 代码是否实现了需求/工票描述的功能
- [ ] 边界情况是否处理（null、空串、边界值、溢出）
- [ ] 并发场景是否考虑（竞态条件、死锁、线程安全）
- [ ] off-by-one 错误、数学精度是否验证
- [ ] 用户可见的变更是否实际验证过（UI 变更要试用）

### 3. 可读性与可维护性
- [ ] 命名是否清晰表达意图（不用缩写，如 `calcRev` → `calculateGrossRevenue`）
- [ ] Java：PascalCase 类名 / camelCase 方法变量 / UPPER_SNAKE_CASE 常量
- [ ] JS/TS：camelCase 变量函数 / PascalCase Vue 组件
- [ ] 数据库：snake_case 表名字段
- [ ] 函数是否短小且职责单一（理想 < 20 行）
- [ ] 代码逻辑是否清晰，新人能否快速理解
- [ ] 是否存在死代码、注释掉的代码块（应删除）
- [ ] 是否有 god class、过度嵌套、魔法数字/字符串
- [ ] 注释只解释 WHY，不解释 WHAT；清除过期 TODO

### 4. 安全
- [ ] 所有用户输入是否校验和清洗（SQL 注入、XSS、CSRF 防护）
- [ ] 敏感信息是否硬编码（API Key、密码、Token → 用 vault/env 配置）
- [ ] 每个接口是否都有鉴权校验（认证 + 授权）
- [ ] 错误信息是否泄露内部细节（不暴露堆栈、数据库结构）
- [ ] 第三方依赖是否有已知漏洞（CVE 检查）
- [ ] 密码是否用 BCrypt 等安全算法存储
- [ ] CORS 配置是否合理

### 5. 性能
- [ ] 算法复杂度是否合理（避免 O(n^2) 能用 O(n) 的场景）
- [ ] 是否有 N+1 查询问题（JPA 用 `@EntityGraph` / `JOIN FETCH`）
- [ ] 大数据量是否分页或流式处理，不全量加载
- [ ] 高频访问数据是否考虑缓存（`@Cacheable`）
- [ ] 资源是否正确关闭（连接、流、文件句柄）
- [ ] 网络请求是否合并（减少不必要的多次调用）
- [ ] `@Transactional` 是否用在正确的粒度（方法级，不在循环内）

### 6. 异常处理与日志
- [ ] 捕获具体异常，不捕获 `Exception` 或 `Throwable`
- [ ] 不吞异常，不用 `printStackTrace`
- [ ] 日志是否包含上下文（用户ID、请求ID、文件名、堆栈）
- [ ] 用户侧错误信息是否友好（不暴露技术细节）
- [ ] 异常路径下资源是否正确释放（try-with-resources / finally）
- [ ] 统一使用 `BizException` + `Result<T>` 包装返回

### 7. 测试
- [ ] 变更是否包含对应的测试代码（同一 CL/PR）
- [ ] 测试是否真正验证核心逻辑（不是只测了 trivial 场景）
- [ ] 是否覆盖了正常路径 + 异常/边界路径
- [ ] 是否用**等价类划分**减少了冗余用例，同时保证覆盖所有等价类
- [ ] 是否用**边界值分析**覆盖了 min / min-1 / max / max+1
- [ ] 多条件业务逻辑是否用**判定表**覆盖了关键条件组合
- [ ] 有状态业务是否测试了**合法/非法状态转换**
- [ ] 是否覆盖错误推测场景：null、空串、重复提交、并发、超时
- [ ] 测试命名是否表达意图（`test_fail_when_duplicate_email` 而非 `test_user`）
- [ ] 测试是否独立、可重复、不依赖执行顺序
- [ ] 测试代码本身是否简洁（测试也需要维护）

### 8. 前端专项（Vue3 + Ant Design Vue）
- [ ] 是否使用 `<script setup>`，没有 Options API
- [ ] 是否有 `any` 类型（严格禁止）
- [ ] Props / Emits 是否定义了类型和校验
- [ ] `v-for` 是否有唯一 `:key`
- [ ] `v-html` 是否处理了 XSS 风险（禁止用于用户输入）
- [ ] 异步操作是否有 loading 状态和错误处理
- [ ] 路由守卫是否正确配置（需登录页面）
- [ ] 组件是否可复用，职责是否单一
- [ ] 计算属性 vs 方法 vs watch 是否选择正确
- [ ] 大列表是否考虑虚拟滚动
- [ ] API 调用是否集中管理（Axios 拦截器统一处理 token/错误）
- [ ] localStorage/sessionStorage 是否存放了敏感信息（XSS 风险）

### 9. 后端专项（Spring Boot）
- [ ] API 返回统一用 `Result<T>` 包装
- [ ] HTTP 状态码是否正确（200/201/204/400/404/500）
- [ ] 接口是否有 Swagger/OpenAPI 文档
- [ ] DTO/VO/Entity 是否分层使用（不直接暴露实体）
- [ ] 入参是否用 `@Valid` + Bean Validation 校验
- [ ] 数据库索引是否加在高频查询字段上
- [ ] 是否有批量插入/更新（避免循环内单条操作）

### 10. 风格与一致性
- [ ] 代码风格是否符合团队规范（ESLint / Checkstyle 通过）
- [ ] 风格变更和功能变更是否分开提交（不混在同一个 PR）
- [ ] 与现有代码库保持一致（优于个人偏好）
- [ ] 格式化是否由工具自动处理（不人工讨论空格/缩进）

### 11. 测试与构建
- [ ] 构建是否通过（`pnpm build` / `mvn clean install`）
- [ ] Lint 是否通过（`pnpm lint`）
- [ ] 测试是否通过（`mvn test`）
- [ ] 提交信息格式：`feat(scope): 描述` / `fix(scope): 描述`

## 二、审查输出格式

```markdown
## 审查结果

### 问题
1. **[严重]** `UserService.java:42` — Service 层直接写了 SQL，违反分层原则
2. **[建议]** `Login.vue:15` — 异步请求缺少 loading 状态和错误处理
3. **[Nit]** `UserMapper.xml:8` — SELECT * 应明确字段，避免多余列传输

### 优点
- 异常处理统一，BizException + @ControllerAdvice 使用规范
- 分页接口设计合理，PageHelper 使用正确
- 单元测试覆盖了主要边界情况
```

**严重程度说明**：
- **[严重]** — 必须修复：安全漏洞、逻辑错误、数据损坏风险、架构违规
- **[建议]** — 强烈建议：性能隐患、可维护性差、缺测试、缺错误处理
- **[Nit]** — 优化建议：命名偏好、风格细节，不阻塞合并

## 三、审查原则（来自 Google & Microsoft）

1. **代码健康度是标准**：代码不需要完美，但必须比修改前更好
2. **优先审批**：一旦变更确实提升了系统整体健康度，即使不完美也应批准
3. **解释 WHY**：每条反馈说明原因，不是只说"改掉"
4. **肯定好代码**：看到好的实践要明确表扬，不要只挑毛病
5. **先看测试**：测试能揭示作者的意图和预期行为，先审测试再审实现
6. **关注上下文**：看完整文件，不只看 diff；评估对系统整体的影响
7. **及时反馈**：审查延迟会阻塞整个团队，安排固定的审查时间
8. **自动化优先**：格式、风格、Lint 等交给工具，人专注于逻辑和设计

## 四、审查流程建议

| 环节 | 要求 |
|------|------|
| 提交前 | 作者自审代码，运行测试，提供清晰的变更说明 |
| 审查量 | 单次审查 < 400 行（Cisco 研究：超过 200 行缺陷发现率急剧下降） |
| 审查时长 | 单次不超过 60 分钟，超过后休息再继续 |
| 审查人数 | 2 名活跃审查者为宜 |
| 反馈优先级 | 正确性 → 设计 → 安全 → 性能 → 可读性 → 风格 |
| 修复确认 | 发现的缺陷必须记录并验证已修复 |
